# Context Switch Commit

## Overview

在开始明显无关的新任务前，先把上一项任务留下的已确认修改收口成一次提交，避免不同主题的改动混在同一工作树里。把“上一项任务”理解为最近一个连续的工作主题，而不是上一条单独消息。

## Trigger Rules

满足以下条件时触发本 skill：

- 当前用户请求与最近一个工作主题明显不同。
- 工作树存在未提交改动，且这些改动大概率属于上一项任务。
- 直接进入新任务会让不同主题的改动混杂，或明显增加后续审阅成本。

不要触发本 skill：

- 用户是在继续同一任务、补充约束、或自然追问。
- 工作树已经干净，没有待提交改动。
- 未提交改动明显属于用户本地工作，或无法可靠归属到上一项任务。
- 用户明确要求先不要提交，或要求把多项工作合并后再提交。

## Workflow

1. 先判断是否真的发生任务切换。不要因为措辞变化就误判；看目标、涉及模块、预期产物是否已经换了题。
2. 运行 `git status --short` 查看是否存在未提交改动。
3. 识别“上一项任务”的文件集合。

- 优先使用当前线程最近几轮对话里已经修改过的文件。
- 如果上一项任务跨多轮对话，把同一主题下的文件视为同一个变更集。
- 只纳入你已经检查过 diff、且能说明其属于上一项任务的文件。

4. 复核提交边界。必要时查看 `git diff -- <path>`，确认不会把新任务或用户自己的改动带进提交。
5. 调用 `$git-session-commit` 的流程提交这些文件。

- 先 `git restore --staged .`
- 再按显式路径暂存上一项任务文件
- 用中文提交信息概括上一项任务，而不是当前新任务

6. 提交完成后，再开始处理新的无关请求。

## Ownership Rules

- 把“上一次”理解为最近一个完整主题，不要求只覆盖上一轮单独消息。
- 如果工作树里混有多个未完成主题，默认只提交最近那个已经足够明确的主题；不要顺手把更早或归属不清的改动一起提交。
- 如果无法安全区分 agent 修改和用户本地修改，不要自动提交；先向用户说明原因，再决定是否继续新任务。

## Response Requirements

- 在开始新任务前，用 1-2 句说明已识别到上下文切换，并先提交上一项任务。
- 如果没有触发自动提交，也要明确说明原因，例如“工作树干净”或“改动归属不清，未自动提交”。
- 汇报提交结果时写清提交信息，以及是否仍有剩余未提交文件。
